## 3. 实际处理顺序

```text
本地三个 Parquet
  → 记录源文件 SHA-256、行数和大小
  → 建立评测图像的 RGB 哈希索引（仅检查重叠）
  → 分片、分批读取训练数据
  → 解码图片、保存 PNG、提取问题和答案
  → 解析选项并映射字母答案
  → 检查精确评测图重叠
  → 按同图同题同选项去重、检查答案冲突
  → 按整张图片固定划分训练与验证
  → 写出 JSONL、逐行审计、清单
  → 复核源文件哈希、训练加载器与最终图片路径
```

三个 Parquet 分开读取，因为图表分片额外含有 `rationale` 列，不能假设三者 schema 完全相同。图片按最多 24 行一批读取，解码和保存使用最多 6 个工作线程；这是处理性能设置，不参与数据划分。

## 4. 图片怎么处理

每条记录要求恰好一个原图。优先读取 `images[0].bytes`；没有内嵌字节时读取 `images[0].path`，相对路径相对于源 Parquet 所在目录解析。

用 Pillow 解码并转换为 RGB，计算图片身份：

```python
image_sha256 = sha256(rgb.tobytes() + str(rgb.size).encode()).hexdigest()
```

保存为 `images/<image_sha256>.png`，使用无损 PNG、`compress_level=1`。没有缩放、放大、裁剪、填充，也没有生成 oracle crop。PNG 文件体积与原始 JPEG 不同，不代表分辨率被修改；一致性比较的是解码后的 RGB 像素及尺寸，不是压缩文件的字节。

另有 `encoded_sha256` 标识原始图片载荷，用于复用同编码图片的解码结果。训练／验证划分使用的是 RGB 像素哈希，**不是**压缩载荷哈希。

这一步只是落盘训练原图。训练时模型自己的标准视觉预处理仍然存在，与本次数据整理分开。

## 5. 问题、答案和选项怎么处理

每个最终训练行只包含五个字段，与 `eav_selfplay.io.load_questions` 的严格接口一致：

| 字段 | 内容与来源 |
|---|---|
| qid | 根据图片、问题、选项计算的稳定标识 |
| question | 优先 `extra_info.question`，其次顶层 `question`；去掉首尾空白 |
| image | 统一图片目录中的绝对 PNG 路径 |
| reference | 优先 `reward_model.ground_truth`，其次 `extra_info.answer`，再其次顶层 `answer`；必要时把选项字母映射为内容 |
| options | 顶层有效选项字典，或从问题文本提取的选项；开放问答为 `{}` |

不使用原始 `prompt` 作为新角色提示，不继承 `rationale`、原系统提示、思维链或工具轨迹。`question` 中原有的题目、公式、选项文字仍保留；不会因为提取出了 `options` 就把原问题中的选项删掉。

### 选项解析与修正

支持 `A. ... / B. ...` 和 `(A) ... / (B) ...` 等连续大写选项标记。要求从 A 开始、顺序连续且内容非空。最终规则优先依据换行后的选项边界；第一个 A 可以紧接问题末尾，例如 `问题?A. ...`。

若标准答案为明确选项字母且能找到对应内容，例如 `reference="B"`、`options["B"]="红色"`，最终 `reference` 写成“红色”。这样奖励核对可以比较答案含义，而不是只比较字母。原始字母保存在 `row_audit.jsonl` 的 `original_reference` 中。

首轮通用规则曾把选项正文里的“矩阵 A.”、“特征 F.”也当作选项边界，导致 69 条有效图表记录暂时被标为无法解析。第二轮修正该规则后，全部 13,659 条图表题的标准答案字母均可映射；这 69 条已恢复，并重新执行去重、冲突检查和划分。**prepared_v1 中的这 69 条不代表原数据无效；最终以 prepared_v2 为准。**

映射与选项提取属于确定性文本规则，不是人工逐题复核，也没有调用模型重新判答案。

## 6. 去重、冲突与无效记录规则

同一个候选记录键由以下三项构成：图片 RGB 哈希、规范化问题、按键排序的选项 JSON。问题规范化仅使用 Unicode NFKC 和空白合并；最终输出的问题文本保留原内容，仅去首尾空白。

```python
key = "\n".join([
    image_sha256,
    norm(question),
    json.dumps(options, sort_keys=True, ensure_ascii=False),
])
qid = sha256(key.encode()).hexdigest()
```

同键且规范化后的答案一致时，按处理顺序保留第一条，其余标为 `excluded_duplicate`；本次 39 条重复均来自 chart。只比较图片相同不足以去重，同图不同问题仍保留。不同图片的相似问题也不会被合并。

同键却出现不同规范化答案时，该键下所有记录都隔离为 `quarantined_conflicting_answers`，不擅自挑一个答案。这里的答案规范化也是 NFKC 加空白合并，不把数学等价式或同义句自动视为同一答案。本次没有此类冲突。

缺问题、缺答案、图片无法解码、图片数量不为 1、无法明确映射的字母答案等会标为 `quarantined_invalid`，记录具体原因。本次最终版本没有这类记录。

所有原始行均保留在 `row_audit.jsonl` 中，包括被去重或隔离的行。`quarantine.jsonl` 本次为空是正常结果，不是未检查。

## 7. 为什么读取 V* Bench 和 HRBench

它们只作为**独立评测集的排重参照**：

- V* Bench：`direct_attributes` 115 张图、`relative_position` 76 张图，共 191 张。
- HRBench：`hr_bench_4k.tsv` 和 `hr_bench_8k.tsv`，各 800 条记录。
- 总计 1,791 条评测图像引用，对应 519 个不同 RGB 像素哈希。引用数不是独立图像数，HRBench 中同图会因不同题目或选项排列重复出现。

训练来源图片若与这些图片的 RGB 哈希完全相同，则该图对应的训练来源记录都排除，状态为 `excluded_evaluation_overlap`。本次匹配数为 **0**，所以没有因此删掉训练数据。`evaluation_overlaps.jsonl` 为空符合本次结果。

该检查覆盖精确解码像素相同的图片，**不证明没有重新压缩、缩放、裁剪或语义近似图片的重叠**。同样，本次训练／验证“图片不交叉”指 RGB 哈希不交叉。

## 8. 训练／验证如何划分

对去重和排除后的图片计算：

```python
heldout = int(image_sha256[:16], 16) / 2**64 < 0.05
```

条件成立的整张图及其全部保留题目进入验证集，否则进入训练集。因此同图的不同问题不会跨组，划分可重复，无须随机打乱。这里的约 95%/5% 是按图片哈希阈值划分，不强制题目数或每个来源都恰好达到 5%。

最终训练 44,673 条、验证 2,340 条，二者 qid 不交叉，RGB 图片哈希也不交叉。验证集是从官方训练数据中留出的内部验证集，**不是 V* Bench 或 HRBench**。

## 9. 已完成的校验及其范围

全量检查：原始行数与所有状态数量相加一致；图片能解码；最终行可由当前训练加载器读取；每行的问题、答案、选项与审计信息一致；最终图片路径存在；qid 唯一；训练与验证不共享 RGB 哈希；没有剩余精确评测图重叠；输出文件 SHA-256 与清单一致。三个源 Parquet 在处理前后 SHA-256 一致。

独立抽样检查：固定随机种子 `20261030`，每个来源抽取 16 条，共 48 条，重新读取保存后的 PNG，核对 RGB 模式、尺寸和像素哈希。这不是对全部 PNG 再做一次像素复核；原始图片已在提取阶段全量解码。

主要证据文件：

| 文件 | 用途 |
|---|---|
| [manifest.json](prepared_v2/manifest.json) | 源文件路径、大小、哈希；分组数量；处理规则；输出文件和脚本哈希 |
| [row_audit.jsonl](prepared_v2/row_audit.jsonl) | 每个原始行的来源、处理状态、原答案、最终答案、选项和图片哈希 |
| [verification.json](prepared_v2/verification.json) | 独立复核结果、抽样种子、48 条图片检查记录 |
| [evaluation_image_index.json](prepared_v2/evaluation_image_index.json) | 评测图片哈希及对应评测记录 |

校验没有重新判断 47k 标准答案的真实性，也没有人工逐条审查所有题目或验证后续裁判的标签质量。数据格式和一致性通过，不等于训练效果已经验证。

## 10. 后续出问题时如何查

### 先复查最终数据

在 CPU 实例运行，不需要启动 GPU worker：

```bash
cd /inspire/hdd/global_user/lichengqi-253108120152/guohyx/Pixel-Reasoner

python3 -B data/deepeyes47k/verify_dataset.py
```

它会读取最终数据、检查路径和哈希，并重新写入 `prepared_v2/verification.json`；不会重新生成训练数据。当前脚本断言了本版本的固定数量，未来有新版本时不能直接拿旧断言套用。

该复查脚本检查的是清单中已记录的源文件完整性结果；它不会重新计算三个源 Parquet 的哈希。若怀疑原始文件后来被改过，可运行下面命令，与 `manifest.json` 的 `sources` 中哈希逐项比较：

```bash
sha256sum \
  /inspire/hdd/global_user/lichengqi-253108120152/DeepEyes/data/benchmarks/DeepEyes-Datasets-47k/data_0.1.2_visual_toolbox_v2.parquet \
  /inspire/hdd/global_user/lichengqi-253108120152/DeepEyes/data/benchmarks/DeepEyes-Datasets-47k/data_thinklite_reasoning_acc.parquet \
  /inspire/hdd/global_user/lichengqi-253108120152/DeepEyes/data/benchmarks/DeepEyes-Datasets-47k/data_v0.8_visual_toolbox_v2.parquet
```

### 定位单条问题

拿到训练记录的 `qid` 后，在 `prepared_v2/row_audit.jsonl` 中查找：

```bash
rg -n --fixed-strings '这里换成实际qid' \
  data/deepeyes47k/prepared_v2/row_audit.jsonl
```

重点查看：`source_file`、`source_row_1based`、`status`、`question`、`original_reference`、`reference`、`options`、`option_method`、`image_sha256`。重复行还会记录被保留行的位置。

`source_row_1based` 是对应 Parquet 的 **1 起始物理行号**。`source_index` 是原数据自带编号，可能重复，不能单独用它定位。

若出现图片找不到，先检查 `images/` 是否仍在原位置；若出现字母与答案内容不一致，核对 `original_reference` 和选项映射；若数量变化，先对比输入文件哈希以及 `manifest.json`，确认没有误用 prepared_v1。

## 11. 完整重建的依赖

本次实际执行顺序为 `prepare_dataset.py → finalize_dataset.py → verify_dataset.py`。第二步依赖首轮清单、图片缓存和评测索引；只执行第一步不能得到本次最终结果。

这些脚本的输出版本路径写在代码中，遇到已存在的输出目录会拒绝覆盖。因此现有目录下不要把重建命令当作断点续跑命令。需要重新制作新版本时，应先审查输出路径和脚本改动，使用新版本位置并保留当前输入及审计材料。

数据整理完成时，训练配置的 `train_data`、`output` 尚未填写；后续已将本数据集接入八卡训练配置，启动方式和实际训练验证状态以 [训练 README](../../README.md) 为准。数据整理本身不代表已开始训练，也不代替首轮裁判质量审查。
